# Stage 1 report: structured extraction from safety data sheets

## Setup
- **Task:** extract 9 fields from a safety data sheet (SDS) into JSON that passes the schema in `src/factory_docs/schema.py`.
- **Documents:** the 35 public SDS with stage 1 in `data/manifest.csv` (en, uk, de, fr, nl, es, sv, pl, it).
- **Golden set:** 10 of those documents, labeled by hand (`data/golden/`). Accuracy is measured only on these 10.
- **Models:**
  - Cloud: `anthropic/claude-haiku-5.5` through OpenRouter, which takes no sampling parameters (`docs/ISSUES.md` I-003).
  - Cloud with sampling: `anthropic/claude-haiku-4.5` through OpenRouter, added on 2026-10-28, with the same two configurations as the local model. It gets only their temperature (1.0 and 0.0), because Claude 4+ models reject `temperature` and `top_p` in one request. It costs 10x Haiku 5.5 per token.
  - Local: `qwen3.5:9b` through Ollama, with two sampling configurations, `default` and `greedy` (`config.toml`).
- **Prompt versions:** v1-v3, in `prompts/`, with the changes and their reasons in `prompts/CHANGELOG.md`.
- **Metric rules:** `docs/METRICS.md`.
- **Hardware:** local latency was measured on an Apple M4 Pro (Ollama's MLX runner, GPU). Speed on a CPU-only laptop was not measured (`docs/ISSUES.md` I-004).

### 1. Comparison signs read the wrong way round (local model)
- **What:** D003 p. 3, section 3: `aceton 67-64-1 … > 99` (% w/w) became min null, max 99 in all 6 qwen runs. D010 p. 3: `Температура спалаху : > 190 °C` became max 190 in 5 of 6. In D007 p. 3, `<0,05%`, `<0,025%` and `<0,0025%` came back as min = max in 4 qwen runs; in 2 more, other wrong bounds (min 0.0, or min 0.05 with max null). Similar bound errors appear in 1-2 qwen runs each in D001, D006, D008 and D010: a lost lower or upper bound, or the D008 flash point (min 65, no max) given as min = max = 65 or as max 65.
- **Why:** the text is clean, and both Haikus read every one of these correctly in all 9 of their runs. So this is the 9B model's reading of `<` and `>`, not the input. In D007 each value sits under a line like `Певна межа концентрації: … C ≥ 0,05 %` (a specific concentration limit), a second number with a sign that the model has to ignore. The same kind of line made D037 schema-invalid with prompt v3 (`prompts/CHANGELOG.md`).
- **Prompt versions:** v2 added a min / max rule with examples, and v3 added temperature examples and "never set min = max". D003 stayed wrong in every run. The rules also brought new errors: nitrogen in D001 (100 %) came back with no concentration in 3 runs (default v2 and v3, greedy v3) and as max 100 only in greedy v2, while all v1 runs got it right (`prompts/CHANGELOG.md`).
- **Likely fix:** do not ask the model for the bound. Let it copy the value as written (`> 99`), and parse the sign in code. That needs a schema change.

### 2. Language from the product name, not the body text (both models)
- **What:** D034 is an English SDS ("Safety data sheet according to Regulation (EC) No 1907/2006"), and its body is English throughout. Page 1 starts with `Trade name: pH-Pufferlösung 12,00` and a supplier address in Gerlingen, Germany. 14 of 15 runs returned `de`; only Haiku 5.5 with v2 returned `en`.
- **Why:** the strongest German cues come first, and the models take them for the document's language.
- **Prompt versions:** the v2 language rule says "A product name in another language does not change it". Haiku followed it in v2, then returned `de` again in v3, where the rule is unchanged. That is run-to-run variance in the cloud model, which has no sampling settings (I-003). Haiku 4.5 returned `de` in all 6 runs, at both temperatures and with every prompt, so for it the rule had no effect. The qwen model returned `de` in all 6 runs, and returned `se` (the country code) for Swedish D002 in all 6, although v2 and v3 say "'sv' (not 'se')".
- **Note:** `se` is a valid ISO 639-1 code (Northern Sami), so a format check cannot catch it.
- **Likely fix:** detect the language in code from the body text, or restrict the field to the languages the system supports.

### 3. Product name or trade name (label rule)
- **What:** D002 p. 1 has `Produktnamn: Nitrogen, komprimerad`, then `Varumärke: BIOGON® N (E941), Nitrogen 3.5 Industrial, …` (15 names). 11 of 15 runs returned the product name. The golden label holds the trade-name list, by the labeling rule that product_name is the trade name (`src/factory_docs/schema.py`). Haiku 4.5 is the only model that returned the list, with v2 and v3 at both temperatures; with v1 it also returned the product name.
- **Why:** "Varumärke" means "brand", so the v2 rule ("if section 1 gives both a product name and a trade name, use the trade name") does not obviously apply. Haiku 4.5 applied it anyway; Haiku 5.5 and qwen did not. The English twin D001 says "Trade name". There the v2 rule fixed both Haikus (v2, v3) and one qwen run (default v2); D001 is still wrong in 8 of 15 runs, all with v1 or on qwen.
- **Note:** this error is as much about the label as about the model. "Nitrogen, compressed" is a reasonable answer to "what is this product".
- **Likely fix:** name the section 1 labels per language in the prompt (Varumärke, Handelsname, Nazwa handlowa), or change the label rule to the product name and keep the trade names in a separate field.

### 4. A hazard statement split by a page break (local model)
- **What:** D010 (`H412 Шкідливо для водних організмів із тривалимі наслідками.`) was missed in all 6 qwen runs, which returned an empty list. Both Haikus found it in all 9 of their runs.
- **Why (likely):** in the PDF itself, section 2 starts at the bottom of page 1, which holds only the acute aquatic category. Page 2 opens with the repeated page header (product name, version, dates, SDS number) and only then gives the chronic category and the H412 line, with the word hyphenated (`наслід-` / `ками`). The output is just `[]`, so the results show the miss but not its cause. The page break is the most visible difference from the documents where qwen finds the statements.
- **Prompt versions:** the v2 rule "every H and EUH statement in section 2" fixed the other hazard-statement misses (EUH066 in D003, EUH208 and EUH210 in D008, all missed by qwen v1), but not this one.
- **Likely fix:** remove repeated page headers and footers before extraction. Stage 2 (RAG) needs that clean-up too.

### 5. Print date taken as the revision date (local model)
- **What:** every page header of D007 has `дата друку: 26.07.2024` (print date) on the left and `змінена версія від: 10.10.2022` (revised version of) on the right. In the extracted text they become one line. 3 qwen runs (default v2 and v3, greedy v3) returned the print date. The schema says to ignore print dates.
- **Why:** the model took the first date on the line, without reading the Ukrainian labels.
- **Prompt versions:** all 3 v1 runs got it right, and v2 and v3 do not mention dates. So this does not come from a prompt rule; it is variance that shows up with the longer prompts.
- **Likely fix:** name the revision-date labels per language in the prompt, or extract all dated labels and pick the revision date in code.

### Pattern
- **Haiku 5.5:** its 8 misses are all on ambiguous inputs. There are errors 2 and 3, plus two v1 errors that the v2 rules fixed (D010 physical_state `liquid` for "крем, паста", D038 signal_word for "Achtung").
- **Haiku 4.5:** its 16 misses over 6 runs are in the same places, and none is one of errors 1, 4 or 5.
  - Error 2: all 6 runs.
  - Errors 3 and its D001 twin: v1 only.
  - D001: with v1 it gave nitrogen no concentration (both temperatures).
  - D010 physical_state: `liquid` with v1, and `solid` with v3. The v3 synonym list ("powder, crystals -> solid") seems to have pulled "крем, паста" to solid.
- **Sampling on Haiku 4.5:** `default` (temperature 1.0) and `greedy` (0.0) returned the same wrong value in every one of these cases, with every prompt. So on the golden set they score the same.
- **qwen3.5-9b:** it also fails where the text is plain but needs reading with care: comparison signs (1), a section split by a page header (4), and date labels (5).
- **Fixes that are not prompts:** the prompt rules fixed most of the misses aimed at simple rules. The errors that remain point to code: sign parsing, language detection and page clean-up.
- **Caveat:** this is 10 golden documents and one run per configuration, and qwen default samples at temperature 1.0. So a 1/15 error can be noise. Errors 1-4 recur in at least 5 of the 6 qwen runs, and errors 2 and 3 also in the Haikus.

## Final choice
**Production choice: Haiku 5.5 (`anthropic/claude-haiku-5.5`) with prompt v2.** It takes no sampling parameters, so it runs with the provider's defaults.

**Why:**
- **Accuracy:** 89 of 90 fields (98.9%) on the golden set, and 35 of 35 schema-valid first responses, so the repair step was never needed.
- **Cost:** $2.01 per 1000 documents, close to free at this volume.
- **Speed:** 2.2 s per document at p50 (4.4 s at p95).
- **Prompt:** v2 scored best on both Haikus. v3 scored 88 of 90; with 10 golden documents and one run per configuration, that 1-field gap is noise, so v3 brings no gain for its longer prompt.

**The alternatives:**
- **Haiku 4.5:** the same accuracy (85 / 89 / 88 of 90 with v1 / v2 / v3, at both temperatures), but $16.32 per 1000 documents with v2, about 8x Haiku 5.5, and slower (3.6-3.9 s at p50). Sampling did not help it on the golden set. For this task it is not worth the price.
- **qwen3.5-9b (local):** better than expected, with 80 of 90 fields at best (greedy, v2) and no API cost. But it was about 13x slower (28.4 s at p50 on the M4 Pro), and it makes the systematic errors 1, 4 and 5 in the error analysis. Of the two alternatives, a local model is the better next step, not Haiku 4.5.

**What would change the choice:**
- **Data protection:** if the documents may not leave the site, a local model is the only option, whatever it costs in accuracy and speed. This is likely to decide the question for real factory documentation, which this project replaces with public documents. The same holds for hospitals and other places where data protection must be at the highest level. The cloud model here is reached through OpenRouter and then an upstream provider (Azure or Amazon Bedrock in these runs), so every document leaves the machine twice.
- **Cost:** without such a rule, a switch to a local model is worth it when all three of these hold:
1. Other local models have been tested on this task and the best of them is chosen. qwen3.5-9b was picked from only three candidates, in a bake-off on three documents.
2. A dedicated machine runs it, not a working laptop. The measured times are from an Apple M4 Pro; laptop speed was not measured (`docs/ISSUES.md` I-004).
3. The volume is large enough that the saved API cost matters, and latency does not. qwen took about 28 s per document, against about 2 s for Haiku 5.5.
