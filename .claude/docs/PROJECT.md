# Project: Industrial Documentation AI Assistant (working title)

> Source of truth for WHAT we are building and WHY. Task-level work lives in `docs/roadmap/`.
> Last updated: 2026-11-25

## 1. Summary
A portfolio-grade AI system built incrementally over an 8-week AI engineering course. It turns open industrial documentation (equipment manuals, safety data sheets, material certificates, technical reports) into structured data, then grows into a cited question-answering system (RAG), an agent that performs multi-step checks with tools, and finally a production-style service (API, security, monitoring, cost tracking).

It is a real portfolio project, not a set of separate homework tasks. Each course assignment is a stage of this one system.

## 2. The problem
In manufacturing, knowledge is scattered across thousands of documents: equipment manuals, raw-material certificates, safety data sheets, process instructions. Finding one parameter ("max operating temperature of pump X", "flash point of solvent Y") means digging through folders and long PDFs. An assistant that extracts, indexes and answers with exact citations saves that time. The cost of a wrong answer is high (safety, quality), so the system must cite sources and say "I don't know" when the documents do not answer.

## 3. Scope and honesty about data
- Real factory documentation is closed. This project uses ONLY open, publicly available documents as stand-ins. State this plainly in the README.
- Audience: global. Multilingual by design (English first). Every document records its language.
- Documents may be PDFs, scans or plain text. Stage 1 works from extracted text.
- Corpus: stage 1 uses only safety data sheets (SDS), which are public, plentiful, and follow a standard 16-section format worldwide (GHS). The other document types (manuals, datasheets, certificates, declarations, hazard notices, product specifications) are kept for stage 2 RAG. See decision 10.

## 4. The four stages (from the course)
1. Structured extraction: raw documents to validated JSON against a schema; compare a paid cloud model with a local model.
2. RAG: document search and answer generation with source citations, plus quality testing.
3. Agent: autonomous multi-step tasks using tools.
4. Service: API, security, monitoring, cost tracking.

Each stage builds on the previous one. Do not design later stages in detail until they start, but avoid choices that block them (section 5).

## 5. Design constraints that carry across stages
- One shared model interface, so cloud and local models are interchangeable.
- Every document has a stable ID and a manifest entry (source URL, license, language, type).
- Preserve page/section boundaries when extracting text, so stage 2 can cite them.
- Every run is logged (model, prompt version, sampling params) and stored in `results/`, so numbers are reproducible. This also becomes the basis for stage 4 cost tracking.
- Everything runs from a fresh clone with one command.

- Extraction schema (decision 7, 2026-10-20, after a survey of the 15 SDS texts): Pydantic models in `src/factory_docs/schema.py`. Fields: product_name, language, signal_word (enum danger/warning/none), physical_state (enum solid/liquid/gas), components (list of {name, cas_number, concentration}), hazard_statements (list of {code, text}), flash_point, un_number, revision_date. - Search stack (decision 13, 2026-11-18, user's choice): Qdrant in local mode + FastEmbed. Embeddings and reranking run inside the Python process, with no server and no per-call cost, and work the same locally and in GitHub Actions. The concrete models are picked in S2-06 and S2-08.
  - **Embedding model (S2-06, 2026-11-19, user's choice):** `google/embeddinggemma-300m` (768 dimensions, 1.26 GB, 2048-token limit, Gemma Terms of Use), config key `embeddinggemma`, with prefixes `task: search result | query: ` and `title: none | text: ` (FastEmbed adds none itself). `make compare-embeddings` measured 6 multilingual FastEmbed 0.9.1 models on all 2433 structure chunks (`data/index/embedding_comparison.md`). EmbeddingGemma is the only one with no chunk over its token limit that is also fast: 202 s, against e5-large 417 s (5 % of chunks over its 512-token limit, 9 % in uk) and qwen3-0.6b-q 760 s (12.6 GB RAM). Its uk and de smoke-query top 5 are as sensible as e5-large's. Rejected: MiniLM-L12 (84 % of chunks over its 128-token limit), mpnet-base and potion-128m (off-topic German top 5), jina-embeddings-v3 (CC BY-NC 4.0, not measured). Measured on the M4 Pro CPU only.
  - **Hybrid search (S2-07, 2026-11-20, user's choices: chunk text only, own tokenizer):** BM25 reads the chunk text only, like the vectors, so S2-10 compares the retrievers on the same input. The tokenizer is ours and language-neutral (NFKC, casefold, Unicode word runs, codes kept whole, no stemming or stopwords; standard library only), because FastEmbed's Bm25 needs one stemmer language per model and splits CAS numbers. BM25 weights are a Qdrant sparse vector `bm25` with Qdrant's IDF, k1 1.2 and b 0.75 (usual defaults, untuned). Fusion is our own RRF with k 60 over 50 candidates per retriever, so each hit shows both ranks and the code is unit-tested. Known limits: `docs/ISSUES.md` I-008.
  - **Reranker and filters (S2-08, 2026-11-20, user's choices):** `BAAI/bge-reranker-v2-m3-int8` (0.57 GB INT8 weights, 8192-token limit, Apache 2.0), config key `bge-m3-int8`, rescoring the first 30 first-stage hits (untuned). `make compare-rerankers` measured the two multilingual FastEmbed 0.9.1 cross-encoders on 3 smoke queries x 30 hybrid candidates (`data/index/reranker_comparison.md`): INT8 4.0 s per query and 2.7 GB RAM against 4.8 s and 3.5 GB for the full 2.27 GB model, no pair over the token limit, and the same 5 chunks in each top 5. INT8 picked for the smaller CI download. Rejected: jina-reranker-v2-base-multilingual (CC BY-NC 4.0), the English-only ms-marco and jina v1 models. `make search` does not rerank by default (`[search] rerank = false`) until S2-10 measures it. Filters (user's choice: derived at index time): `make index` adds `is_latest` (no other document in the collection supersedes it), `doc_date` (parsed from `version_or_date`; a partial date counts as its first day; undated D016-D018 drop out of a date filter) and `languages` (`de/en` counts as de and en) to each payload, and Qdrant applies the filter inside each retriever, before ranking.
  - **Default search setup (S2-10, 2026-11-21, user's choice: pick on the gold set and say so):** hybrid + reranking (`[search] rerank = true`). `make eval-retrieval` measured vector, bm25, hybrid and hybrid+rerank on both chunkings for the 15 gold questions (`evals/results/retrieval.md`). By the rule written before the run (on `structure`: highest MRR@10, then recall@5, then no reranker), hybrid+rerank wins with MRR@10 0.615 and recall@5 13/15, against 0.482 and 10/15 for hybrid alone. The cost is about 5 s per query on the M4 Pro CPU, against 0.04 s. No numeric setting was tuned on the gold set; REPORT.md says the pick was made on it.
  - **Chunking for answers (decision 19, S2-10, 2026-11-21, user's choice): keep `structure`.** With hybrid+rerank, `fixed` retrieves better (MRR@10 0.703, recall@5 14/15, against 0.615 and 13/15; `evals/results/retrieval.md`), but four questions decide the gap (R08, R07, R02, R11). A fixed chunk carries the section where it starts, and the answer usually sits in the next one: `make section-labels` (S2-12) finds that every chunk holding the gold quote carries a correct label for 4 of 15 questions with `fixed` against 15 of 15 with `structure`, and over the whole corpus 42.9 % of fixed (chunk, block) pairs against 100 % (structure is correct by construction). An earlier by-eye check had said 13 of 15 for `structure`; the script counts R13 through its D044 evidence, since its D042 evidence has no headings in either strategy. Citations must name the section (S2-13), so a wrong label is worse than a lower rank. Rejected: switch to `fixed` as is (wrong sections in most citations); label each fixed chunk with every section it spans (re-chunk and re-index, and citations stay vague). Contextual chunk headers (stretch) may close the retrieval gap.
