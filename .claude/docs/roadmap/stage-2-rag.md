## Goal
Build a full RAG slice on the project corpus, from raw documents to answers with source citations, with answer quality checked by an automatic eval pipeline in CI. The stage 3 agent will work on this corpus.

`documents (PDF / DOCX / HTML) -> cleaning -> chunks + metadata -> vector DB (hybrid search + reranking) -> answer with sources -> evals in CI`

## Course requirements (summary of the assignment)
- **Step 1, corpus and chunking (about 4 h):**
  - At least 30 public documents in at least 2 formats (PDF, DOCX, HTML, Markdown), no personal data.
  - Ingestion keeps structure (headings, lists, tables), cleans and normalizes (headers and footers, line-break hyphens, encoding, HTML boilerplate) and deduplicates by content hash. Near-duplicates are optional.
  - Chunking strategy justified in the README (why this size and this way of splitting) and compared with fixed-size chunking on at least a few documents.
  - Chunk metadata: source, title, section, date or version, document hash.
  - Output: a chunks file (for example `chunks.jsonl`) and a manifest.
- **Step 2, index and hybrid search (about 4 h):**
  - Embeddings (provider or local) stored in a vector DB (Qdrant, Chroma, FAISS or similar).
  - Hybrid search: BM25 + vector search with merged results.
  - Reranking and metadata filters (for example date, document type, access group).
  - Search quality on 10-15 questions with a known correct chunk, using recall@k or MRR, comparing at least 2 configurations (vector only / hybrid / hybrid + reranking).
- **Step 3, RAG with sources (about 4 h):**
  - Answers use only retrieved chunks and cite the document and section for every claim.
  - Token budget for the context. When the documents hold no answer, the system says so and does not make one up.
  - Prompts in versioned files with a changelog, as in stage 1.
- **Step 4, test set and evals in CI (about 4 h):**
  - At least 20 questions with expected answers and sources, including questions with no answer in the corpus and trap questions (similar documents, outdated versions).
  - Deterministic scorers where possible: correct source cited, key facts present, "I don't know" where expected.
  - LLM judge for the rest, calibrated on at least 10 hand-graded answers, reporting how often it agrees with the human.
  - Faithfulness check: every claim is supported by the context.
  - Evals run in CI on every push or pull request, and the run fails below a threshold.
  - `REPORT.md`: retrieval and answer metrics, 3-5 characteristic errors (expected, actual, why), and what to improve next.
- **Stretch (no points):** semantic or parent-child chunking with comparison, contextual chunk headers, incremental ingestion, embedding cache.
- **Technical:** Python 3.10+, one-command run (`make run` or `python main.py`), any answer and embedding model, cost per 1000 questions if the model is paid, keys only in `.env` with `.env.example` committed, one public GitHub repo link.
- **Repo must contain:** ingestion, indexing, RAG and eval code; `data/` with the corpus (or a download script) and manifest; `prompts/` with versions and changelog; `evals/` with test set, scoring functions and run results; `.github/workflows/` (or similar) running the evals; `REPORT.md`; `README.md` (what it is, how to run, chunking rationale).
- **Not needed:** UI, deployment, fine-tuning, a large corpus (30-100 documents is enough), perfect accuracy.
- **Common mistakes that lose points:**
  - Fixed-size chunking with no justification or comparison.
  - No "I don't know", so the model invents answers.
  - An LLM judge not checked against human grades.
  - An AI-generated test set that nobody reviewed.
  - Search quality not measured.
